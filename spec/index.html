Users and journeys

Five roles, three key journeys.

Visitor

Not signed in

See the landing page and privacy notice; sign in; sign up

Member

A person with a profile

Create and edit their own profile; choose recruiter visibility; preview what recruiters see

Recruiter (pending)

Signed up, not yet approved

Sign in and see "waiting for approval". Nothing else

Recruiter (approved)

Approved by an admin

Search members who opted in; view their profiles and graphs

Admin

The team (a few accounts set by hand)

Approve or revoke recruiters in the Firebase console

06

Search, graphs and quality

The exact matching rules, the graphs, the limits, and how each layer will be tested.

How matching and ranking workwith a worked example used as a unit test

Inputs: Must = must-have skills, Nice = nice-to-have skills, Keywords = free words, rmin = minimum rating (default 3).

  1. Names are compared ignoring case and using the alias list (PROF-04).
  2. Filters (years, country) remove people first.
  3. For each must-have: score = rating ÷ 5 if the person has it and rating is at least rmin, else 0. Must = average over the must-haves.
  4. Nice = average of rating ÷ 5 over the nice-to-haves (0 where the person lacks it).
  5. Keywords = share of the typed words found in headline, summary, role titles or company names.
  6. Score = 100 × (0.7·Must + 0.2·Nice + 0.1·Keywords). If a group is empty, its weight is shared out in proportion among the other groups. Round to a whole number.
  7. Strict mode (default) excludes anyone with a must-have scoring 0. Otherwise they stay in, ranked by score, and are marked.

Worked example for the unit tests. Search: must-have Python and SQL, nice-to-have Docker, rmin 3, no keywords, so the weights become Must 0.7778 and Nice 0.2222.

Database rules sketchillustrative, final rules are written and tested in the plan
{
  "rules": {
    "users": {
      "$uid": {
        ".read": "auth != null && auth.uid === $uid",
        "role":     { ".write": "auth.uid === $uid && !data.exists()",
                      ".validate": "newData.val() === 'member' || newData.val() === 'recruiter'" },
        "approved": { ".write": "root.child('admins').child(auth.uid).val() === true",
                      ".validate": "newData.isBoolean()" }
      }
    },
    "profiles": {
      "$uid": { ".read": "auth.uid === $uid && auth.token.email_verified === true",
                ".write": "auth.uid === $uid && auth.token.email_verified === true" }
    },
    "publicProfiles": {
      ".read": "auth.token.email_verified === true && root.child('users').child(auth.uid).child('role').val() === 'recruiter' && root.child('users').child(auth.uid).child('approved').val() === true",
      "$uid": { ".write": "auth.uid === $uid && auth.token.email_verified === true" }
    }
  }
}

A rule that grantsaccess at a parent path cannot be tightened at a child, so the structure above grants access only at the lowest level needed. Members also need to read their own publicProfiles/{uid} for the preview; that will be added with its own test.
